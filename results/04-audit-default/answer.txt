Found four concrete mismatches or enforcement gaps:

1. **“Already resolved” is not strictly enforced.** README lines 103–104 describe `--finalize` as operating on an already-resolved debate; lines 172–174 say drafting runs *only* after resolution. But [`parseRespondeoStatus`](src/debate.ts:124) treats everything except a first nonempty line matching `STATUS: NEEDS_INPUT` as `RESOLVED`, including empty text, malformed status, and saved judge-failure text. [`--finalize`](src/index.ts:234) uses that permissive check. Failed judge text is actually saved by the normal workflow ([generation](src/debate.ts:263), [write](src/index.ts:378)), so this is reachable without manually corrupting artifacts. Fake-CLI checks confirmed that failed and empty determinations both permit drafting.

2. **`--continue` does not require a `NEEDS_INPUT` determination.** [README lines 95–97](README.md:95) and [177–181](README.md:177) describe answering an unresolved judge’s questions. The [continuation branch](src/index.ts:255) never checks the previous status, although its [prompt](src/debate.ts:170) asserts that the determination ended in `NEEDS_INPUT`. Fake-CLI checks confirmed that resolved and failed determinations are also accepted.

3. **The configured-judge requirement has undocumented exceptions.** [README lines 158–160](README.md:158) say the judge and subsequent phases run only when configuration defines a `judge`. That holds for a fresh debate ([code](src/index.ts:340)), but both closing commands select the **current configuration’s judge**, falling back to Claude Opus, high effort, $5 per turn ([default](src/index.ts:103), [selection](src/index.ts:209)). They do not restore the original debate’s judge. Thus the README’s closing examples can silently switch judges when the original run used another configuration.

4. **The stdout fallback description is wrong for continuations.** [README lines 107–110](README.md:107) promise `final-report.md` when produced, otherwise `debate.md`. An unresolved continuation instead prints the new `respondeo-N.md` and exits **0** ([code](src/index.ts:270)). A resolved continuation whose final-report drafting fails also prints that determination path and exits **0** ([code](src/index.ts:278)). Both behaviors were reproduced with fake CLIs.

The important workflow claims otherwise hold:

- **Phase order:** a fresh debate requires two successful proposals, completes its reaction rounds, then runs the configured judge. Recognized `NEEDS_INPUT` and failed judge turns suppress drafting; a recognized resolution triggers it ([implementation](src/debate.ts:228)). `--finalize` drafts directly without re-judging.
- **Saved determination selection:** `--debate` wins; otherwise selection uses the lexically latest `debate-*` directory under the current working directory’s `.debate`. Within it, both commands select the highest numbered `respondeo*.md`, treating `respondeo.md` as version 1 ([implementation](src/index.ts:124)). They do not search backward for a resolved version.
- **Repository evidence:** the README correctly associates `--repo` with grounding the deliverable ([usage](README.md:99), [phase description](README.md:172)). Initial judging and continuation receive transcript context without a repository worktree; drafting receives `--repo` or the current configuration’s `repo` and runs in a disposable worktree of HEAD ([calls](src/debate.ts:188), [initial judging](src/debate.ts:261), [worktree](src/debate.ts:70)). Continuation invokes only the judge, not the debaters.
- **Successful stdout:** successful drafting prints `final-report.md`. A fresh debate without a deliverable prints `debate.md`, as documented ([closing commands](src/index.ts:249), [fresh debate](src/index.ts:403)).
